**CloudWatch metrics and the agent**
- Retention: data points with a period **under 60 seconds** are available for **3 hours** (high-resolution custom metrics); **60 seconds** for **15 days**; **300 seconds** for **63 days**; **3600 seconds** for **455 days (15 months)**; data published with a shorter period is aggregated for long-term storage (1-minute data: 1-minute resolution for 15 days, then 5-minute, then after 63 days 1-hour); metrics with no new data for two weeks disappear from the console list but stay retrievable — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html
- EC2 basic monitoring: status check metrics in **1-minute** periods, all other metrics in **5-minute** periods, no charge; detailed monitoring: **1-minute** periods, charged per metric; can be turned on at launch or on a running or stopped instance — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/manage-detailed-monitoring.html
- `AWS/EC2` instance metrics: `CPUUtilization`, `DiskReadOps`/`DiskWriteOps`/`DiskReadBytes`/`DiskWriteBytes` (**instance store volumes only**), `NetworkIn`/`NetworkOut`, CPU credit metrics, status check metrics, EBS metrics for Nitro instances — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/viewing_metrics_with_cloudwatch.html
- “Amazon EC2 doesn’t provide metrics related to operating system (OS) memory usage or disk usage metrics”; install the unified CloudWatch agent — https://repost.aws/knowledge-center/cloudwatch-memory-metrics-ec2 · alarms on disk or memory metrics stuck in `INSUFFICIENT_DATA` when the agent is missing; agent metrics in the **`CWAgent`** namespace — https://repost.aws/knowledge-center/cloudwatch-alarms-insufficient-data-ec2
- CloudWatch agent: collects **metrics, logs and traces** from EC2 instances, **on-premises servers** and containerised applications; in-guest system-level metrics; custom metrics over **StatsD** (Linux and Windows) and **collectd** (Linux); logs from Linux and Windows Server; default namespace **`CWAgent`**; agent metrics are billed as custom metrics; can be installed manually or with AWS Systems Manager; logs land in CloudWatch Logs “just like logs collected by the older CloudWatch Logs agent” — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Install-CloudWatch-Agent.html · example config with `mem_used_percent` and `disk_used_percent`; storing the agent configuration in **Parameter Store** is a best practice — https://repost.aws/knowledge-center/cloudwatch-agent-metric-visibility · per-process metrics with the **`procstat`** plugin (default collection interval 60 seconds) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Agent-procstat-process-metrics.html · swap measurements (`swap_used…`) in the Linux `metrics_collected` section — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Agent-Configuration-File-Details.html · IAM role with **`CloudWatchAgentServerPolicy`** (plus **`AmazonSSMManagedInstanceCore`** for Systems Manager) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Solution-EC2-Health.html
- ⚑ The **CloudWatch Logs agent** is **deprecated**; “we strongly recommend using the newer unified CloudWatch agent”; with IMDSv2 the unified agent is required — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/AgentReference.html
- Custom metrics: **standard resolution** = one-minute granularity, **high resolution** = one second (retrieve at 1, 5, 10, 30 s or multiples of 60 s); every `PutMetricData` call is charged; alarms on high-resolution metrics can use a **10-second or 30-second** period (higher charge) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/publishingMetrics.html (the alarm-evaluation page also lists 20 s; the lesson says “as short as 10 seconds”)
- Metric streams: continuous stream of CloudWatch metrics through **Amazon Data Firehose** to S3 or any Firehose destination (JSON or OpenTelemetry) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-metric-streams-setup-datalake.html
- Compute Optimizer analyses `mem_used_percent` in the **`CWAgent`** namespace (Linux) when the agent is installed — https://docs.aws.amazon.com/compute-optimizer/latest/ug/ec2-metrics-analyzed.html (boundary sentence only; Session 12)
- Billing metric data is stored in **US East (N. Virginia)** and represents worldwide charges; billing alerts must be enabled first — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/monitor_estimated_charges_with_cloudwatch.html

**Alarms**
- States `OK`, `ALARM`, `INSUFFICIENT_DATA`; settings **Period**, **Evaluation Periods** (N), **Datapoints to Alarm** (M): “M out of N”, breaching points need not be consecutive; evaluation interval = N × period (4 of 5 at 1 minute = 5 minutes; 3 of 3 at 10 minutes = 30 minutes); alarms with periods of one minute or more are evaluated every minute — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation.html
- Missing data: `missing` (default; all points in the range missing → `INSUFFICIENT_DATA`), `notBreaching`, `breaching`, `ignore` (keep the current state); `AWS/DynamoDB` alarms default to ignore; for EC2 alarms with stop/terminate/reboot/recover actions AWS recommends `missing`; the two worked tables (3 of 3 and 2 of 3, evaluation range 5) are reproduced in the `alarmSim` widget exactly; with fewer real points than Evaluation Periods, CloudWatch fills the gap with the missing-data treatment but includes every real point, so M real breaching points within the window are enough for `ALARM` under any treatment (the widget’s part 1 derives “first ALARM” this way: 1 of 5 → minute 2, re-read 2026-11-11) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html · breaching points need not be consecutive, “but they must all be within the last number of data points equal to Evaluation Period” — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation.html
- Actions: **SNS** topic; ⚑ **invoke a Lambda function** (“the easiest way … to automate custom actions”); **EC2 actions** (stop, terminate, reboot, recover) on EC2-metric alarms; **Auto Scaling** group or Application Auto Scaling target; **Systems Manager OpsItem** or Incident Manager incident (ALARM only); start an investigation; actions run on state transitions (Auto Scaling actions repeat); alarms also emit EventBridge events; composite alarms cannot trigger Auto Scaling actions — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-actions.html (no launch date printed: none was read)
- Composite alarms: a rule expression over the states of other alarms; reduces alarm noise (alert only on the composite) — https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cloudwatch-compositealarm.html
- Anomaly detection: statistical and machine-learning model of expected values (a band); alarms on above, below or both; accounts for hourly, daily, weekly seasonality and trends — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Anomaly_Detection.html
- Cross-account observability: **monitoring account** linked to **source accounts** (Observability Access Manager sinks and links, or Organizations) for metrics, logs, traces, Application Signals, Application Insights and Internet Monitor, **within a Region**; a separate cross-account cross-Region dashboard feature exists — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Unified-Cross-Account.html

**CloudWatch Logs**
- Log groups never expire by default; retention per log group from **one day to 10 years**; expired data cannot be recovered — https://repost.aws/knowledge-center/cloudwatch-prevent-logs-deletion
- Metric filters turn matching log events into CloudWatch metrics to graph or alarm on; “Filters do not retroactively filter data”; Standard log class only — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html
- Subscription filters: real-time feed to **Kinesis Data Streams, Amazon Data Firehose or Lambda** (and OpenSearch Service), usually **less than three minutes** after ingestion; ⚑ **up to five subscription filters per log group** and ⚑ **one account-level subscription filter per Region**; Standard log class only; retries for up to 24 hours — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Subscriptions.html
- Cross-account log streaming: the receiving account creates a **CloudWatch Logs destination** that wraps a Kinesis Data Streams stream; sender accounts create subscription filters pointing to it (an organization can be the sender) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CrossAccountSubscriptions-Kinesis.html
- Export to S3 (`CreateExportTask`): log data “can take up to **12 hours** to become available for export”; AWS recommends subscriptions, not regular exports, for continuous archiving; same or another account — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/S3Export.html
- ⚑ Log classes **Standard** and **Essentials (formerly Infrequent Access)**: Essentials has a lower ingestion price and lacks metric filters, subscription filters, Live Tail, anomaly detection, embedded metric format, `GetLogEvents`/`FilterLogEvents` (use Logs Insights); both support KMS encryption, export to S3 and masking; the class cannot be changed after the log group is created — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CloudWatch_Logs_Log_Classes.html
- ⚑ **Cross-account cross-Region log centralization**: centralization rules from the management or delegated administrator account copy log groups of chosen accounts, OUs or the whole organization into a destination account and Region (optional backup Region) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CloudWatchLogs_Centralization.html
- Logs Insights: priced per query, by the amount of ingested log data scanned — https://aws.amazon.com/cloudwatch/faqs/ · Live Tail: watch new log events as they arrive, filter by pattern — https://aws.amazon.com/blogs/mt/announcing-live-tail-feature-for-amazon-cloudwatch-logs/
- Who writes logs: VPC Flow Logs to CloudWatch Logs, S3 or Firehose (already verified in Session 3 ch11); the ECS task execution role sends container logs (Session 10 ch9); a CloudTrail trail can deliver to a log group (CloudTrail row below); RDS Enhanced Monitoring writes `RDSOSMetrics` (RDS row below).

**Dashboards, Insights, synthetic and real-user monitoring, X-Ray**
- Contributor Insights: top-N contributors in log data (“find top talkers”), rules analyse incoming data in real time, built-in rules for other services — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/ContributorInsights.html
- Container Insights and Lambda Insights: correlated metrics, logs and traces for containers (ECS, EKS) and Lambda functions — https://aws.amazon.com/cloudwatch/features/
- Synthetics canaries: configurable scripts on a schedule that follow customer routes against endpoints and APIs, “even when you don’t have any customer traffic”, discover issues before customers do; run as Lambda functions in your account; “can store load time data and screenshots of the UI” (the ch7 sorter row) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Synthetics_Canaries.html
- RUM: client-side data from actual user sessions of web and mobile apps; data retained **30 days** — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-RUM.html
- X-Ray: **segments** (one per compute resource), **subsegments** (downstream calls; inferred segments for services such as DynamoDB), **traces** (all segments of one request, by trace ID), **service graph / trace map**; default sampling: **the first request each second and five percent of additional requests**; **annotations** indexed for filter expressions, **metadata** not indexed — https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html · API Gateway: active tracing on a **REST API stage** (X-Ray traces REST APIs only) — https://docs.aws.amazon.com/xray/latest/devguide/xray-services-apigateway.html
- ⚑ **X-Ray SDKs and daemon in maintenance mode since 25 February 2026** (security fixes only, no new features); AWS recommends migrating to **OpenTelemetry** to send traces to X-Ray — https://docs.aws.amazon.com/xray/latest/devguide/xray-sdk-daemon-timeline.html · the CloudWatch agent can receive OpenTelemetry or X-Ray traces and send them to X-Ray without a separate daemon — Install-CloudWatch-Agent page above
- ⚑ **Application Signals**: automatic instrumentation, standard dashboards (requests, availability, latency), **service level objectives** — https://aws.amazon.com/blogs/mt/how-to-monitor-application-health-using-slos-with-amazon-cloudwatch-application-signals/
- ⚑ **CloudWatch Evidently discontinued** (effective 17 October 2025 per the blog; printed as “October 2025”); feature flags → **AWS AppConfig** — https://aws.amazon.com/blogs/mt/support-for-amazon-cloudwatch-evidently-ending-soon/ (no docs page with the date was found; only the month is printed)

**CloudTrail**
- Enabled by default; **event history** = viewable, searchable, downloadable, immutable record of the **past 90 days of management events in a Region**; no CloudTrail charge; shows management events only (no data, Insights or network activity events); single account, single Region, one attribute filter; for longer, create a trail — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/view-cloudtrail-events.html
- Trails: deliver events to **S3**, optionally **CloudWatch Logs** and **EventBridge**; multi-Region (all trails created in the console) or single-Region; **organization trail** created in the management account or a delegated administrator, member accounts **see it but cannot modify or delete it** and by default cannot read its log files; console trails encrypt log and digest files with a **KMS key by default**, otherwise S3 server-side encryption; log files published about every **5 minutes**, delivery “within an average of about 5 minutes” (not guaranteed); **one copy of ongoing management events delivered free** (S3 storage charged); a multi-Region trail sends all Regions to one log group — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/how-cloudtrail-works.html
- Event types: management (control plane), **data events** (resource operations such as S3 object reads and writes; high volume; **not logged by default**; additional charges; not in event history) — https://docs.aws.amazon.com/AmazonS3/latest/userguide/cloudtrail-logging-s3-info.html · data events include Lambda function execution (the **`Invoke`** API), S3 object-level calls and SNS `Publish`; off by default, charged — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html · DynamoDB **item-level** calls (`GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `Query`, `Scan` …) are data plane events that need data event logging; control-plane calls such as `DeleteTable` are logged by default — https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/logging-using-cloudtrail.html · **Insights events** (unusual API call rate or error rate against a baseline; not logged by default; charged; may take up to 36 hours to start) — how-cloudtrail-works · ⚑ **network activity events** (API calls through your VPC endpoints) — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-network-events-with-cloudtrail.html · ⚑ **aggregated events** (data events summarised over five-minute windows) — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-aggregated-events.html
- Log file integrity validation: **SHA-256** hashing and **SHA-256 with RSA** signing; a **digest file every hour** referencing the last hour’s log files, delivered to the same bucket in a separate folder; validate with the AWS CLI — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html
- ⚑ **CloudTrail Lake no longer open to new customers from 31 May 2026**; existing customers continue; only critical bug and security fixes; “for capabilities similar to CloudTrail Lake, explore CloudWatch” (AWS recommends migrating to CloudWatch); trails, Insights and aggregated events unaffected — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-lake-service-availability-change.html
- Alarms on CloudTrail events: turn on CloudWatch Logs delivery for the trail, create a metric filter on its log group, alarm to an SNS topic (AWS’s worked example: console sign-in failures) — https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudwatch-alarms-for-cloudtrail.html
- EventBridge receives AWS API calls through CloudTrail (“AWS API Call via CloudTrail”); read-only management events only with the rule state `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` — https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-service-event-cloudtrail-management.html

**Systems Manager**
- Managed node = SSM Agent installed and able to reach the Systems Manager service; AWS, on-premises and multicloud; no bastion hosts, SSH or remote PowerShell needed — https://docs.aws.amazon.com/systems-manager/latest/userguide/what-is-systems-manager.html · instance profile with **`AmazonSSMManagedInstanceCore`** (or `AmazonSSMManagedEC2InstanceDefaultPolicy`); private subnets need the `ssm`, `ssmmessages` and `ec2messages` interface endpoints — https://docs.aws.amazon.com/managedservices/latest/userguide/ssm-agent-auto-install.html
- ⚑ **Default Host Management Configuration**: Systems Manager manages all EC2 instances in an account and Region **without an instance profile** (a default IAM role it applies) — https://docs.aws.amazon.com/systems-manager/latest/userguide/fleet-manager-default-host-management-configuration.html
- Run Command: remotely and securely manage configuration of managed nodes, one-time changes at scale; no additional cost on EC2 nodes — https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command.html
- Patch Manager: **patch baselines** with auto-approval rules; **Scan** (report missing patches) or **Scan and install**; methods: ⚑ a **patch policy in Quick Setup** (recommended; one policy for an organization’s accounts and Regions), a Host Management configuration (scan only), a **maintenance window** task, or on demand — https://docs.aws.amazon.com/systems-manager/latest/userguide/patch-manager.html
- State Manager: an **association** defines the state to maintain (software installed and running, ports closed), reapplied on a schedule and applied to new nodes in a dynamic target group — https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_CreateAssociation.html
- Automation: runbooks for maintenance, deployment and **remediation** across AWS services; AWS-maintained or custom; concurrency and error thresholds — https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-automation.html
- Maintenance Windows: schedules for disruptive actions such as patching — https://docs.aws.amazon.com/systems-manager/latest/userguide/maintenance-windows.html · Inventory: collects metadata only (applications, files, network configuration, Windows updates, services) — https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-inventory.html · OpsCenter: OpsItems, created automatically from CloudWatch alarms or EventBridge events, resolved with Automation runbooks — https://docs.aws.amazon.com/systems-manager/latest/userguide/OpsCenter.html · Distributor: package and publish software (for example the CloudWatch agent) to managed nodes, installed with Run Command or State Manager — https://docs.aws.amazon.com/systems-manager/latest/userguide/distributor.html
