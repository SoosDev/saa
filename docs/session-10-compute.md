## Facts verified 2026-11-11 (AWS MCP documentation tools: `search_documentation`, `read_documentation`)

Every row below was read on the page itself by the implementer; ⚑ rows contradict or extend older course material and get a “Changed since the exam guide” callout. No drill’s or bite’s correct answer depends on a ⚑ row (launch templates are the answer under old and new material alike). Units are printed as each page prints them (the Fargate task table says GB, the June 2026 announcement says GiB).

**EC2: families, bursting, hibernation, tenancy**
- Instance categories: General purpose (web servers, code repositories, small-to-medium databases), Compute optimized (batch processing, media transcoding, dedicated game servers), Memory optimized (in-memory databases, data analytics, enterprise applications), Accelerated computing (hardware accelerators: floating point, graphics, pattern matching), Storage optimized (high sequential read and write access to very large data sets on local storage), HPC optimized — https://aws.amazon.com/ec2/instance-types/compute-optimized/ · HPC optimized: “the best price performance for running HPC workloads at scale”, for “complex simulations, deep learning, and visual effects rendering” — https://aws.amazon.com/ec2/instance-types/hpc-optimized/ · storage optimized IOPS are printed without a number (the instance-types page says “tens of thousands”)
- Burstable credits: earned below the baseline, spent above it; **standard** mode bursts on accrued credits, then comes down to the baseline; **unlimited** mode spends surplus credits and is billed when the average CPU over a **24-hour** period exceeds the baseline — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-credits-baseline-concepts.html · surplus credits not paid down are charged at “a flat additional rate per vCPU-hour” — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode-concepts.html
- ⚑ **T8i, T4g, T3a and T3 launch as `unlimited` by default**; surplus credits are charged when the 24-hour average exceeds the baseline; T3 on a Dedicated Host launches `standard` (unlimited not supported there); AWS recommends standard mode for Spot Instances — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-unlimited-mode.html
- Hibernation: RAM saved to the EBS root volume, instance ID kept, processes resumed; no instance-usage charge while hibernated (EBS storage is charged); used to pre-warm slow-starting instances — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Hibernate.html · enabled **at launch** only (not on an existing instance); Linux RAM **less than 150 GiB**, Windows **16 GiB or less**; root volume EBS and **encrypted**; no bare metal — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/hibernating-prerequisites.html
- Dedicated Instances: hardware dedicated to one customer, may share hardware with the same account’s non-dedicated instances; Dedicated Host: a physical server for your use, for existing **per-socket, per-core or per-VM** licences — https://docs.aws.amazon.com/help-panel/aws-backup/latest/helppanel/ec2-tenancy.html · Host: visibility of sockets and physical cores, **affinity** (same host after stop/start), instance placement controls, License Manager — https://aws.amazon.com/ec2/dedicated-hosts/ · Hosts priced per physical host, Dedicated Instances give no placement visibility or control — https://docs.aws.amazon.com/decision-guides/latest/decision-guides/ec2-purchasing-options-aws-how-to-choose.html · Hosts paid On-Demand, with a **Dedicated Host Reservation** or with **Savings Plans** — https://aws.amazon.com/ec2/dedicated-hosts/pricing/

**Placement groups**
- Cluster: one AZ (cannot span AZs), high-bisection-bandwidth segment; enhanced networking: up to **10 Gbps single-flow** inside the group, **5 Gbps** outside; recommended one launch request and one instance type; burstable (T) types not supported; reserve capacity with an On-Demand Capacity Reservation (zonal RIs cannot reserve inside a placement group); Capacity Blocks do not support placement groups — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/placement-strategies.html
- Partition: partitions share no racks; **at most seven partitions per AZ**; instance count limited only by the account; can span AZs; HDFS, HBase, Cassandra; partition visible to topology-aware applications; Dedicated Instances at most two partitions — same page
- Spread: each instance on distinct hardware; can span AZs; **at most seven running instances per AZ** (21 in a three-AZ Region; an eighth does not launch; use several groups beyond that); not for Dedicated Instances — same page
- ⚑ **Precision time** placement groups: the fourth strategy (enhanced Amazon Time Sync, PTP hardware clock on Linux, microsecond-accurate clocks; no additional charge; can be the parent of a cluster group) — same page
- EFA: network device with OS-bypass for low-latency MPI traffic; recommended in a placement group in one AZ; not supported across AZs — https://docs.aws.amazon.com/parallelcluster/latest/ug/efa-v3.html · built for tightly coupled HPC — https://aws.amazon.com/blogs/aws/now-available-elastic-fabric-adapter-efa-for-tightly-coupled-hpc-workloads/

**Purchase options (matched to the workload; no prices)**
- Savings Plans: commitment in **$/hour** for **1 or 3 years**; **Compute Savings Plans up to 66%** off On-Demand, any family, size, Region, OS, tenancy, **and Fargate and Lambda**; **EC2 Instance Savings Plans up to 72%**, one instance family in one Region, any size, OS, tenancy; **no capacity reservation**; **do not apply to Spot**; cannot be cancelled during the term — https://docs.aws.amazon.com/savingsplans/latest/userguide/sp-ris.html
- ⚑ **Four** Savings Plans types: Compute, EC2 Instance, **Database (up to 35%)**, SageMaker AI (up to 64%) — https://docs.aws.amazon.com/savingsplans/latest/userguide/plan-types.html
- Reserved Instances: Standard up to 72% (like EC2 Instance SP), Convertible up to 66% (like Compute SP); 1- or 3-year term — sp-ris page · Standard: cannot be exchanged, **can be sold and bought** in the RI Marketplace; Convertible: **can be exchanged** (family, type, platform, scope, tenancy), cannot be sold or bought in the Marketplace; both can modify some attributes — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/reserved-instances-types.html · Zonal RIs reserve capacity in one AZ, Regional RIs reserve none — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html
- ⚑ AWS now calls RIs “an older purchasing option that we generally recommend replacing with Savings Plans” and “a legacy option”; newer instance families might not support RI pricing (decision guide, last updated 22 Jun 2026) — https://docs.aws.amazon.com/decision-guides/latest/decision-guides/ec2-purchasing-options-aws-how-to-choose.html
- On-Demand Capacity Reservations: capacity in **one AZ** for any duration; immediate-use reservations have **no term commitment** and can be cancelled at any time; billed whether used or not; **no billing discount**, combine with Savings Plans or Regional RIs for one — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html · ⚑ **future-dated** reservations: minimum commitment duration **14 days** for C, G, I, M, R and T instances, **12 weeks** for U and X (printed as “at least 14 days for most instance types”) — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservations-create.html
- ⚑ **Capacity Blocks for ML**: GPU instances reserved for a defined period starting on a future date (training, fine-tuning, experiments); 1 to 182 days; not combinable with Savings Plans or RI discounts — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservation-overview.html · decision guide
- Spot: interruptible capacity **up to 90%** off; **two-minute** interruption notice as an EventBridge event and in instance metadata; **rebalance recommendation** signals elevated risk earlier; checkpoint long jobs — decision guide · interruption behaviour **stop, hibernate or terminate** (default terminate) — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/interruption-behavior.html
- ⚑ Spot pricing: “prices are set by Amazon EC2 and adjusted gradually based on long-term supply and demand trends … without the complexity of bidding mechanisms that were used historically” — decision guide · AWS recommends not setting a Spot maximum price (the default maximum is the On-Demand price) — https://docs.aws.amazon.com/autoscaling/ec2/userguide/mixed-instances-groups-set-up-overview.html
- ⚑ Spot blocks (defined duration, 1–6 hours): not available to new customers since **1 July 2021**, supported for earlier users until **31 December 2022** — https://aws.amazon.com/blogs/aws/new-ec2-spot-blocks-for-defined-duration-workloads/
- ⚑ Allocation: **price-capacity-optimized** recommended in most cases; lowest price “not recommended” — decision guide · fleets of Spot and On-Demand: **Auto Scaling group** recommended, else EC2 Fleet; **Spot Fleet “uses a legacy API with no planned investment”, strongly discouraged** — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/which-fleet-method-to-use.html

**Auto Scaling**
- ⚑ Launch configurations: no new instance types since **1 Jan 2023**; accounts created on or after **1 Jun 2023** cannot create them in the console; on or after **1 Oct 2024** by any method; cannot be modified once created; migrate to **launch templates** — https://docs.aws.amazon.com/autoscaling/ec2/userguide/create-launch-config.html · a mixed instances group starts from a launch template — mixed-instances-groups-set-up-overview
- Health checks: default **EC2 status checks and scheduled events**; **ELB**, VPC Lattice and EBS health checks must be turned on; custom health checks; an instance not `running` is replaced at once — https://docs.aws.amazon.com/autoscaling/ec2/userguide/health-checks-overview.html
- Health check grace period: **300 s** by default in the console, **0 s** from the CLI or an SDK; 0 turns it off; with a launch lifecycle hook it can be 0 — https://docs.aws.amazon.com/autoscaling/ec2/userguide/health-check-grace-period.html
- Cooldown: default **300 s**; applies to **simple** scaling policies; target tracking and step scaling can scale out at once (instances have a warmup instead); unhealthy instances are replaced without waiting; AWS recommends **not** using simple scaling and cooldowns; ELB deregistration waits **300 s** by default — https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-scaling-cooldowns.html
- Target tracking: pick a metric and a target, Auto Scaling creates and manages the CloudWatch alarms, “similar to how a thermostat maintains a target temperature”; several policies on different metrics: scale out if any is ready, scale in only if all are — https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-scaling-target-tracking.html
- Predictive scaling: needs **at least 24 hours** of data, analyses up to the past **14 days**, hourly forecast for the next **48 hours**, refreshed every **6 hours**; starts in forecast-only mode; **does not scale in** (add dynamic policies) — https://docs.aws.amazon.com/autoscaling/ec2/userguide/predictive-scaling-policy-overview.html
- SQS backlog per instance: `ApproximateNumberOfMessages` ÷ InService instances; target = acceptable latency ÷ average processing time; example **1,500** messages, **10** instances, **0.1 s**, **10 s** → target **100**, backlog **150**, scale out by **five**; a target on queue length alone does not account for instances — https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-using-sqs-queue.html
- Lifecycle hooks: wait states on launch and terminate, **one hour by default**; a hook does not stop a Spot interruption (two-minute notice); Capacity Rebalancing replaces at-risk Spot Instances — https://docs.aws.amazon.com/autoscaling/ec2/userguide/lifecycle-hooks.html
- Warm pools: pre-initialised instances kept **Stopped, Running or Hibernated** — https://docs.aws.amazon.com/eks/latest/APIReference/API_WarmPoolConfig.html (EC2 Auto Scaling warm pool) · instances entering a warm pool are stopped or hibernated — lifecycle-hooks page
- Mixed instances: On-Demand **base capacity** first, then **On-Demand percentage above base** (0–100), the rest Spot; fractions **round up in favour of On-Demand**; examples: base 10, 50/50 → at 20: 15 On-Demand, 5 Spot; at 40: 25 and 15; base 0, 60/40 → at 10: 6 and 4; base 0, 100/0 → no Spot; flexible across at least **10** instance types recommended; **Capacity Rebalancing** — https://docs.aws.amazon.com/autoscaling/ec2/userguide/mixed-instances-groups-set-up-overview.html

**Elastic Load Balancing**
- Types: ALB = application layer (HTTP/HTTPS), path-based routing; NLB = transport layer (TCP/UDP, layer 4), retains the client’s source IP, fixed IP for the life of the load balancer; GWLB = fleets of third-party virtual appliances (firewalls, IDS/IPS) that support **GENEVE**; CLB = TCP/SSL or HTTP/HTTPS; ALB/NLB/GWLB targets register in **target groups**, CLB instances directly — https://docs.aws.amazon.com/autoscaling/ec2/userguide/autoscaling-load-balancer.html
- Target types: ALB instance, IP, **Lambda** (ALB is the only load balancer with Lambda targets); NLB instance, IP, **ALB** — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html · https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-target-groups.html
- ALB requires **at least two** AZs; ELB DNS TTL **60 s**; NLB: one network interface per enabled AZ with a static IP, optionally **one Elastic IP per AZ** at creation; ALB routing: listener rules in priority order, round robin by default; NLB: flow hash, one target per TCP connection; GWLB ↔ appliances over GENEVE port **6081** — https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html · https://docs.aws.amazon.com/elasticloadbalancing/latest/gateway/target-groups.html · GWLB keeps each flow on one appliance with **5-tuple** stickiness by default (3-tuple or 2-tuple optional) — https://docs.aws.amazon.com/elasticloadbalancing/latest/gateway/edit-target-group-attributes.html
- Cross-zone: on → each of 10 targets gets **10%**; off with 2 targets in one AZ and 8 in the other → **25%** each and **6.25%** each; ALB: **always on at the load balancer level**, ⚑ can be turned off per target group; NLB and GWLB: **off by default**, can be turned on — how-elastic-load-balancing-works
- ⚑ NLB listeners: **TCP, TLS, UDP, TCP_UDP, QUIC, TCP_QUIC**; a TCP listener on 443 passes TLS through to targets that decrypt; default actions can weight several target groups (0–999); listener rules exist **only on dual-stack NLBs** and route by **source IP address type** (IPv4 vs IPv6). Printed wording: “an NLB works at layer 4 and cannot route by URL path or host name” — https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-listeners.html
- ⚑ NLB security groups: supported (announced 10 August per the AWS Containers blog); an NLB created without security groups cannot get them later — https://aws.amazon.com/blogs/containers/network-load-balancers-now-support-security-groups/ · https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-troubleshooting.html
- ALB target groups: deregistration delay **300 s** by default; algorithms round robin (default), least outstanding requests, weighted random — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html · NLB target-group stickiness by source IP — load-balancer-listeners
- ALB over CLB: path, host and HTTP header conditions; redirects; fixed responses; IP and Lambda targets; authenticating users through corporate or social identities; NLB over CLB: one Elastic IP per subnet — https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/migrate-classic-load-balancer.html · ALB target groups can use protocol version **HTTP/2** or **gRPC** — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html · ALB supports **WebSockets** natively — https://aws.amazon.com/elasticloadbalancing/faqs/ · NLB is “capable of handling **millions of requests per second** while maintaining ultra-low latencies” — https://aws.amazon.com/elasticloadbalancing/network-load-balancer/
- ⚑ Classic Load Balancer: “the previous generation load balancer … not recommended for new environments”; in Elastic Beanstalk the load balancer type cannot be changed after the environment is created — https://docs.aws.amazon.com/help-panel/elasticbeanstalk/latest/helppanel/f-load-balancer-type.html

**Containers**
- ECS capacity: launch types **EC2, Fargate, External** and ⚑ **ECS Managed Instances**; capacity providers FARGATE, FARGATE_SPOT, Auto Scaling groups, Managed Instances; a strategy cannot mix provider types; capacity providers recommended over launch types — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/capacity-launch-type-comparison.html
- ⚑ ECS Managed Instances (posted **30 Sep 2025**, six Regions at launch): ECS provisions, scales and patches (**every 14 days**) EC2 instances in your account; GPU, network-optimised or burstable types allowed; a management charge on top of EC2 — https://aws.amazon.com/about-aws/whats-new/2025/09/amazon-ecs-managed-instances/
- Fargate task sizes (ECS): **0.25 vCPU with 512 MiB** up to **16 vCPU with 120 GB**; ⚑ **32 vCPU with 60, 120 or 244 GB** (the task table’s unit) — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-tasks-services.html · ⚑ announced **5 Jun 2026**: 32 vCPU with **60 GiB, 120 GiB or 244 GiB**, Linux x86 and Arm, Fargate and Fargate Spot, Compute Savings Plans apply — https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-ecs-fargate-32vcpu/ · older material: 4 vCPU with up to 30 GB (the table’s 4-vCPU row)
- Fargate ephemeral storage: at least **20 GiB**, up to **200 GiB** (platform 1.4.0+) — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-storage.html
- Fargate on EKS: Pods must match a **Fargate profile**; **no DaemonSets** (use a sidecar), **no privileged containers**, no HostPort/HostNetwork, **no GPUs**; **private subnets** only; ALB/NLB with **IP targets** only; EFS mounts automatically, **no EBS volumes**; **EKS does not support Fargate Spot** — https://docs.aws.amazon.com/eks/latest/userguide/fargate.html
- Fargate Spot (ECS): **two-minute** warning as an EventBridge task state change and SIGTERM; Fargate does not replace Spot capacity with On-Demand — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-capacity-providers.html
- Task execution role = the ECS container and Fargate **agents** (pull from a private ECR repository, send logs to CloudWatch Logs, fetch Secrets Manager / Parameter Store values in the task definition); the **task role** = what the application code in the container needs — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html
- ⚑ EKS Auto Mode: AWS manages compute autoscaling, networking, load balancing, storage and upgrades; nodes have a **21-day maximum lifetime** — https://docs.aws.amazon.com/eks/latest/userguide/automode.html
- ⚑ App Runner: “no longer open to new customers” — https://docs.aws.amazon.com/apprunner/latest/dg/what-is-apprunner.html · “will no longer accept new customers starting on **April 30, 2026**”; existing services keep running; AWS recommends **Amazon ECS Express Mode** — https://aws.amazon.com/apprunner/
- ⚑ ECS Express Mode (posted **21 Nov 2025**): from a container image to an HTTPS service with an AWS-provided domain name, ALBs (up to **25** Express services behind one), scaling; no additional charge; all resources stay editable in your account — https://aws.amazon.com/about-aws/whats-new/2025/11/announcing-amazon-ecs-express-mode/
- Choosing (AWS container decision guide): ECS when you need control over network and security configuration; EKS for the flexibility and control of Kubernetes, typically where teams already run Kubernetes; Batch among the vertical solutions — https://docs.aws.amazon.com/decision-guides/latest/decision-guides/choosing-aws-container-service.html

**Lambda (two numbers only) · Elastic Beanstalk · AWS Batch**
- Lambda: **15 minutes**; container images up to **10 GB** — already verified in `docs/session-09-serverless.md` (https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). Everything else: Session 9 ch8.
- Beanstalk deployment policies: **All at once** (fastest, downtime), **Rolling** (batches, reduced capacity), **Rolling with additional batch** (full capacity), **Immutable** (new instances in a separate Auto Scaling group, quick rollback, needs enhanced health reporting), **Traffic splitting** (canary; enhanced health and an ALB); rolling ones only for load-balanced environments — https://docs.aws.amazon.com/help-panel/elasticbeanstalk/latest/helppanel/f-deployment-policy.html
- Blue/green: deploy to a second environment, **Swap environment URLs** (CNAME swap); do not terminate the old environment until DNS has expired; blue/green is **required** to move to an incompatible platform version; the environment must run independently of the production database; Beanstalk **Cluster** environments also support blue/green via CNAME swap — https://docs.aws.amazon.com/elasticbeanstalk/latest/dg/using-features.CNAMESwap.html
- Worker tier: Auto Scaling group, EC2 instances, IAM role, and an SQS queue; a daemon on each instance reads the queue and sends each message to the application — https://docs.aws.amazon.com/elasticbeanstalk/latest/dg/concepts-worker.html · **no additional charge** for Beanstalk — https://aws.amazon.com/elasticbeanstalk/pricing/
- ⚑ Beanstalk **Standard Mode** and **Cluster Mode** (released **17 Sep 2026**): Cluster Mode runs several applications on shared infrastructure powered by Amazon EKS; no additional charge for Cluster Mode, you pay for the EKS cluster and EKS Auto Mode — https://docs.aws.amazon.com/elasticbeanstalk/latest/relnotes/release-2026-09-17-cluster-mode.html
- AWS Batch: job definitions, job queues (priorities), compute environments on ECS (EC2 On-Demand or Spot), Fargate or Fargate Spot, or an existing EKS cluster; Batch provisions and scales the capacity; job dependencies; multi-node parallel jobs and EFA for tightly coupled HPC; allocation strategies best fit, best fit progressive, Spot capacity-optimized — https://aws.amazon.com/batch/features/ · **no additional charge** — https://aws.amazon.com/batch/pricing/
